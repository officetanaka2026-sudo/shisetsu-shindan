# 記事を書くときのルール

`src/content/guides/` に Markdown を1ファイル追加すると記事が増えます。書式は `src/lib/guides.ts` の先頭コメントのとおりです。

## 絶対に守ること
- **事実だけを書く。** 架空の事例、架空のお客様の声、架空の数字（「導入実績◯件」「満足度◯%」など）は書かない。当社にはまだ実績がない。
- 法令・制度・統計は、**公的機関などの一次情報を確認してから**書き、本文の末尾に「参考」として出典のリンクを付ける（国交省、経産省、資源エネルギー庁、建築研究所、自治体など）。確認できないことは書かない。
- 料金は直接数字で書かず、料金トークン（`{{price:...}}`。一覧は `src/lib/priceTokens.ts`）を使う。値引きや「最安」をうたわない。
- 撮影は提携パイロットが行う。当社が自社で機体を持っている、または資格者が在籍していると読める書き方はしない。
- 順位を保証する、必ず見つかる、などの断定はしない。赤外線で分かるのは「異常の候補」。

## 記事の形
- フロントマター：`title`、`description`、`service`、`published`。
  - `title` は狙う検索語を前半に入れる。32文字前後が目安。
  - `description` は 80〜120文字。175文字以内にする（テストで確認される）。
- 冒頭の段落で、検索した人の疑問に答えを先に書く。
- 見出し（`##`）は4〜7個。本文は全体で 2,500〜5,000字程度。
- 表や番号付きリストを使い、比較や手順を分かりやすくする。
- 本文の途中に `{{estimate}}`、末尾に `{{service}}` を必ず入れる（テストで確認される）。
- 内部リンクを2本以上入れる。関連する既存記事（`/guides/スラッグ`）や、サービスページ（`/services/solar` など）へ。
- 既存記事と同じ検索語を狙わない。近い記事がある場合は、新しい記事を書く代わりに既存記事を加筆する。
- 文体は「です・ます」。専門用語には短い説明を付ける。

## 書いたあと
1. `docs/seo/keyword-plan.md` の該当行を「公開」にして、スラッグを書く。
2. 関連が強い既存記事やサービスページ（`src/content/services.ts` の `guides`）からも新しい記事へリンクを張る。
3. `npm run lint && npm run typecheck && npm test && npm run build` がすべて通ることを確認する。
